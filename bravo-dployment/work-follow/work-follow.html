01 · Foundation

Architecture overview

Three tiers separated by HTTPS: a static frontend served by nginx, an API tier on Node, and a data tier holding Mongo for state, Redis for sessions/rate-limit, and disk for media. PawaPay sits outside as a webhook partner for mobile-money flows.

  • 1. config.js

Data model (ERD)

User is the root entity. Listeners become Artists by creating an Artist document. Songs belong to one Artist; albums group songs. Payments, subscriptions, and withdrawals all reference User + Artist for the money trail.

06 · Identity

Authentication

Email/password login returns a short-lived access token (15 min) and a refresh token (30 days, stored in Redis). The frontend's authService intercepts 401s, refreshes silently, and retries the original request.

sequenceDiagram
    autonumber
    participant U as User
    participant F as authService
(frontend)
    participant API as /api/auth
    participant DB as Mongo
    participant R as Redis

    Note over U,R: Login
    U->>F: submit email + password
    F->>API: POST /login
    API->>DB: find user by email
    API->>API: bcrypt.compare
    API->>R: store refresh token (30d)
    API-->>F: { accessToken, refreshToken, user }
    F->>F: localStorage.set, broadcast 'auth:login'
    F-->>U: redirect to #home

    Note over U,R: Silent refresh on 401
    U->>F: any authed request
    F->>API: GET /something (Bearer ...)
    API-->>F: 401 expired
    F->>API: POST /refresh-token
    API->>R: validate refresh token
    API-->>F: new accessToken
    F->>API: retry original request
    API-->>F: 200 OK
Backend
  • routes/authRoutes.js
  • controllers/authController.js
  • middleware/auth.js
Frontend
  • services/authService.js
  • pages/LoginPage.js
  • pages/RegisterPage.js
Gotcha
  • Access token in memory
  • Refresh token in Redis
  • Both rotate on refresh
07 · Identity

Password reset

Time-boxed token sent by email. The reset URL contains a one-time token; submitting a new password consumes it.

sequenceDiagram
    autonumber
    participant U as User
    participant F as Frontend
    participant API as /api/auth
    participant DB as Mongo
    participant Mail as Mailer

    U->>F: enter email on #forgot-password
    F->>API: POST /forgot-password
    API->>DB: find user
    API->>DB: store reset token + expiry (1h)
    API->>Mail: send link with token
    Mail-->>U: email with reset URL

    U->>F: clicks link → #reset-password?token=...
    F->>F: read token from query
    U->>F: enters new password
    F->>API: POST /reset-password { token, password }
    API->>DB: find user by valid token
    API->>API: hash new password
    API->>DB: save user, clear token
    API-->>F: 200 OK
    F-->>U: redirect to #login

09 · Content

Song upload

Multipart form streamed through multer directly to disk. The Song document is created only after the file lands safely. Large videos use the same path with a higher size cap (600 MB at the nginx layer).

sequenceDiagram
    autonumber
    participant U as Artist/Admin
    participant F as UploadForm
    participant N as nginx
    participant Mul as Multer
    participant Ctrl as songController
    participant DB as Mongo
    participant FS as Disk

    U->>F: pick audio + cover + metadata
    F->>N: POST /api/admin/upload-song
(multipart, streaming)
    N->>Mul: proxy_request_buffering off
    Mul->>FS: write audio to /uploads/audio/...
    Mul->>FS: write cover to /uploads/covers/...
    Mul->>Ctrl: req.files populated
    Ctrl->>Ctrl: validate genre, isPremium, title
    Ctrl->>DB: Song.create({...})
    DB-->>Ctrl: saved song
    Ctrl-->>F: 201 { song }
    F-->>U: toast 'Uploaded'
refresh list

    alt File write fails
        Mul-->>Ctrl: error
        Ctrl-->>F: 500
        Note over Ctrl,FS: Partial files cleaned by cron
    end
Limits
  • Audio: 20 MB
  • Video: 600 MB
  • Cover: 5 MB
Validation
  • MIME type allowlist
  • Magic-byte sniffing
  • Genre enum check

11 · Content

Stream & premium gating

Every play hits /api/songs/:id/stream first — the backend authorizes, increments play count atomically, then redirects to the actual file URL. The audio element follows the 302. Range requests after that go directly to nginx.

sequenceDiagram
    autonumber
    participant U as User
    participant AP as AudioPlayer
    participant API as /api/songs
    participant DB as Mongo
    participant N as nginx

    U->>AP: click play
    AP->>API: GET /:id/stream
    API->>DB: find song
    API->>API: check song.isPremium

    alt Premium song + no subscription
        API-->>AP: 403 'Subscription required'
        AP-->>U: show upgrade modal
    else Free, or premium + active sub
        API->>DB: $inc playCount atomically
        API->>DB: insert Analytics event
        API-->>AP: 302 redirect to /uploads/audio/...
        AP->>N: GET /uploads/audio/... Range: bytes=0-
        N-->>AP: 206 Partial Content (zero-copy)
        AP-->>U: audio plays
    end

    Note over AP,N: All subsequent range requests
(scrubbing) go straight to nginx,
not Node — fast and parallel.
Why redirect?
  • Node never touches bytes
  • Auth happens once, up front
  • nginx handles all ranges

13 · Content

Search

Debounced 150ms after each keystroke. Backend uses ReDoS-safe substring regex on indexed fields. Results stream back as the user types — no "enter to search" gesture required.

sequenceDiagram
    autonumber
    participant U as User
    participant SP as SearchPage
    participant API as /api/search
    participant DB as Mongo

    U->>SP: types 'a'
    SP->>SP: q.length < 2, skip
    U->>SP: types 'af'
    SP->>SP: start 150ms timer
    U->>SP: types 'afr' (cancels timer)
    SP->>SP: restart 150ms timer
    Note over SP: 150ms idle...
    SP->>API: GET /songs?q=afr&page=1
    API->>API: escapeRegex(q) — ReDoS-safe
    API->>DB: $or [
title regex,
artist.stageName regex,
genre regex
]
    DB-->>API: matching songs
(.lean() for speed)
    API-->>SP: { songs, totalPages }
    SP-->>U: render results in tabs
Indexed fields
  • Song.title
  • Artist.stageName
  • Album.title
  • genre + isPremium
14 · Money

Subscription purchase

PawaPay STK push is async — the user authorizes on their phone, the webhook arrives some seconds later. The frontend polls for status while showing a waiting screen.

sequenceDiagram
    autonumber
    participant U as User
    participant F as Subscription page
    participant API as /api/subscriptions
    participant PP as PawaPay
    participant Phone as User's phone

    U->>F: pick plan, enter phone
    F->>API: POST /initiate { phone, plan }
    API->>API: create Subscription (status: pending)
    API->>PP: deposit request
    PP-->>API: { transactionId, status: 'submitted' }
    API-->>F: { pollUrl, txId }
    PP->>Phone: STK push prompt
    F-->>U: 'Check your phone'

    U->>Phone: enter mobile-money PIN
    Phone->>PP: confirm

    par Webhook (preferred)
        PP->>API: POST /webhook (signed)
        API->>API: verify HMAC
        API->>API: mark Subscription 'active'
        API->>API: set expiresAt = now + 30d
        API->>Socket: emit 'subscription:activated'
        Socket->>F: real-time update
    and Polling (fallback)
        F->>API: GET /status/:txId (every 3s)
        API-->>F: 'active' once webhook fires
    end

    F-->>U: 'Welcome to Premium' + redirect

    Note over API,PP: Webhook is the source of truth.
Polling is just a UX nicety.
15 · Money

Artist withdrawal

Withdrawals are NOT auto-processed — admin reviews each request before triggering the PawaPay payout. This prevents fraud and gives a manual checkpoint.

sequenceDiagram
    autonumber
    participant A as Artist
    participant Adm as Admin
    participant API as /api/wallet
    participant DB as Mongo
    participant PP as PawaPay

    A->>API: POST /withdraw { amount, phone }
    API->>DB: check wallet.balance >= amount
    API->>DB: create Withdrawal (status: pending)
debit wallet (hold)
    API-->>A: 'Awaiting admin review'
    API->>Socket: emit 'withdrawal:new' to admin

    Adm->>API: GET /admin/withdrawals?status=pending
    Adm->>API: POST /admin/withdrawals/:id/approve

    API->>PP: payout request
    PP-->>API: { transactionId }
    API->>DB: mark Withdrawal 'approved' + txId

    PP-->>A: SMS 'You received K500'
    PP->>API: webhook 'payout success'
    API->>API: verify HMAC
    API->>DB: mark Withdrawal 'paid'
    API->>Socket: emit 'withdrawal:paid' to artist

    alt PawaPay rejects
        PP->>API: webhook 'payout failed'
        API->>DB: refund wallet, mark 'failed'
        API->>Socket: emit to artist + admin
    end
Atomicity
  • Wallet debit + Withdrawal create
  • happen in one transaction
  • refund auto-fires on failure
